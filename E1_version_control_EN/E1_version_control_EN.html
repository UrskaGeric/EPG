Practical 1: Version control with Git and GitHub

🌐 Slovenska različica

Learning goals

After this practical you will be able to:

  • explain what version control is and why it matters for reproducible science,
  • tell the difference between Git (a tool on your computer) and GitHub (an online service),
  • install and configure Git and connect it to your GitHub account,
  • create a repository, clone it to your computer and use the basic commands status, add, commit, push and pull,
  • use Git directly from RStudio,
  • set up your own EPG repository, where you will upload the scripts from all practicals until the end of the semester.

What is version control?

You probably know a folder containing analysis.R, analysis_v2.R, analysis_v2_corrected.R and analysis_FINAL_really.R. A month later you no longer know which one is the right one or what you changed in each. Version control solves this systematically: it saves every important change as a snapshot of the project, together with the time, the author and a short description.

For research this matters because of:

  • reproducibility: you can always show which version of a script produced a result in a paper,
  • safety: if you break or delete something, you can go back to an earlier working state,
  • collaboration: several people can work on the same project without overwriting each other’s files,
  • backup: a copy of the project is stored online, not only on your laptop.

Most of the tools we use in bioinformatics (PLINK, R packages, pipelines such as Snakemake) are developed and published on GitHub. Journals increasingly require the code to be publicly available when a paper is published, most often in a GitHub repository.

Git and GitHub

Git is a version control program that you install on your computer. It records changes locally and works without an internet connection. GitHub is an online service that hosts copies of Git repositories. It enables sharing, collaboration and backup.

Git GitHub
What it is a program (tool) an online service
Where it runs locally, on your computer online (github.com)
How we use it command line, RStudio, VS Code web browser, GitHub Desktop
Purpose recording versions of files in a repository storing and sharing a copy of the repository, collaboration
Alternatives – (de facto standard) GitLab, Bitbucket

Git and GitHub talk to each other mainly through two commands: with push you send your changes to GitHub, with pull you bring changes from GitHub to your computer.

NasvetKey idea

Git stores snapshots of your project (commits) on your computer. GitHub stores a shared copy of that history online, so that you (from several computers) and your collaborators can stay in sync.

Git is a distributed version control system: every user has the complete repository with its full history and a working copy of the files on their own computer. The server (e.g. GitHub) is only a shared point through which users synchronise.

How Git works: where your code lives

When you work with Git, files move between four “places”:

Component Where What it is
Working directory your computer the folder with the files you edit (in RStudio, VS Code, Excel …)
Staging area (index) your computer a “waiting room” for the changes you selected with git add
Local repository your computer (hidden .git folder) the history of all snapshots (commits) on your computer
Remote repository e.g. GitHub the shared online copy of the project

Changes stay local until you send them to GitHub with push. Changes made by others (or by you on another computer) are brought in with pull.

The pull command is actually a combination of two commands: fetch (download the changes from GitHub into the local repository) and merge (combine them with the files in your working directory).

Installation and setup

GitHub account

  1. Go to https://github.com/ and choose Sign up.
  2. Choose your username carefully, as it will appear in the links to your repositories (e.g. https://github.com/name-surname). We recommend a name you can keep using later in your research.
  3. As a student you can apply for the free GitHub Education package (Student Developer Pack). You do not need it for the practicals, but it is useful.

Installing Git

Windows: download Git from https://git-scm.com/download/win and install it with the default settings. The installation also includes Git Bash, the command line in which we will run the commands, and Git Credential Manager, which takes care of signing in to GitHub.

macOS: open the Terminal app and type git --version. If Git is not installed yet, the system will offer to install the Command Line Developer Tools. Confirm.

Linux: sudo apt install git (Ubuntu/Debian).

Check that the installation works. Open Git Bash (Windows) or Terminal (macOS/Linux) and type:

git --version
git version 2.46.0.windows.1

First configuration: who you are

Git signs every commit with a name and an e-mail address. You set this once on every computer. Use the same e-mail address as for your GitHub account:

git config --global user.name "Name Surname"
git config --global user.email "your.address@example.com"
git config --global init.defaultBranch main

The last line makes sure the main branch in new repositories is called main (the same as on GitHub).

Check the settings with:

git config --global --list
NasvetConfiguration from R

You can do the same from the R console with the usethis package:

install.packages("usethis")
usethis::use_git_config(user.name = "Name Surname",
                        user.email = "your.address@example.com")

Signing in to GitHub from your computer

GitHub no longer accepts your account password for push. It needs a secure sign-in:

  • Windows: the first time you git clone (a private repository) or git push, a Git Credential Manager window opens. Choose Sign in with your browser and confirm the access in the browser. The sign-in is saved, so you will not have to repeat it.
  • macOS/Linux, or if the above does not work: create a Personal Access Token (PAT) and store it. The easiest way is from R:
install.packages(c("usethis", "gitcreds"))
usethis::create_github_token()   # opens GitHub in the browser; create the token and copy it
gitcreds::gitcreds_set()         # paste the token when asked
OpozoriloA token is like a password

Never write the token into scripts and never upload it to GitHub.

First repository in Git Bash

We first learn the commands in the command line. This way you will understand what happens in the background when you later click buttons in RStudio.

Create a repository on GitHub

  1. On GitHub click + (top right) → New repository.
  2. Fill in:
    • Repository name: e.g. git-practice
    • Visibility: Private or Public
    • tick Add a README file. The README is the “home page” of the repository with a short description of the project.
  3. Click Create repository.

git clone: download the repository to your computer

On the repository page click the green Code button and copy the HTTPS address. Other options are also available:

Option When to use it
HTTPS cloning with git clone (Git Bash, RStudio)
Open with GitHub Desktop if you prefer a graphical program
Download ZIP a one-off download without the Git history. Do not use it for the practicals.

In Git Bash, move to the folder where you want to keep your projects and clone the repository:

mkdir -p ~/GitHub
cd ~/GitHub
git clone https://github.com/USERNAME/git-practice.git
Cloning into 'git-practice'...
remote: Enumerating objects: 3, done.
remote: Counting objects: 100% (3/3), done.
remote: Total 3 (delta 0), reused 0 (delta 0), pack-reused 0
Receiving objects: 100% (3/3), done.

Move into the new repository folder:

cd git-practice

Git Bash shows some useful information in the command line: the user name and computer in green, the current folder in yellow and, when you are inside a Git repository, the current branch in blue (e.g. (main)).

The (main) label appears only when you are inside a Git repository folder. If you move out (cd ..), it disappears. This way you always see whether you are in the right place.

Look at what is in the folder. The ls -a command also lists hidden files and folders (those starting with a dot):

ls -a
./  ../  .git/  README.md

You created README.md on GitHub. .git/ is a hidden folder where Git stores the entire history of the project: all commits, branches and the link to GitHub. This folder is what turns an ordinary folder into a Git repository. If you delete it, the files stay, but the history is lost and the (main) label disappears. Never edit the .git folder by hand.

NasvetHow to see hidden folders

The .git folder is hidden (all files and folders starting with a dot are hidden). Every repository must have it: if a folder does not contain it, the folder is not a Git repository. You can see hidden folders like this:

Where Command or setting
Git Bash, terminal on macOS/Linux ls -a (all files), ls -la (all, with details)
Windows PowerShell Get-ChildItem -Force (or dir -Force)
Windows command prompt (cmd) dir /a
R list.files(all.files = TRUE)
RStudio, Files tab gear icon (More) → Show Hidden Files
File Explorer (Windows) View → Show → Hidden items
Finder (macOS) Cmd + Shift + period

You can also check whether a folder is a repository with git status: outside a repository it prints fatal: not a git repository.

git status: what has changed?

git status is the command you will use most often. It shows the state of the working directory compared to the last commit.

git status
On branch main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean

Add a new file to the folder, e.g. scripts/test.R (create a scripts folder and an empty file in it). Run git status again:

On branch main
Your branch is up to date with 'origin/main'.

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        scripts/

nothing added to commit but untracked files present (use "git add" to track)

New files that Git does not track yet (untracked) are shown in red.

git add: stage changes

git add scripts/test.R   # one file
git add .                # all changes in the current folder (careful!)

Check again with git status. Files ready to be committed are shown in green:

Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
        new file:   scripts/test.R

git commit: save a snapshot

git commit -m "Add test script"
[main 0c879b4] Add test script
 1 file changed, 0 insertions(+), 0 deletions(-)
 create mode 100644 scripts/test.R

Every commit gets a unique identifier (hash, here 0c879b4) that you can later use to return to it.

NasvetA good commit message

The message should briefly say what you changed, e.g. Add SNP filtering by MAF or Fix y axis on PCA plot. Avoid messages such as fixes, asdf or new version. A month later they will tell you nothing.

Shortcut: git commit -a

git commit -a -m "Update existing scripts"

This command stages and commits changes to already tracked files in one step. It does not add new (untracked) files. Until you get used to Git, prefer the separate git add and git commit steps.

git push: send changes to GitHub

git push
To https://github.com/USERNAME/git-practice.git
   c82b3ae..0c879b4  main -> main

Refresh the repository page on GitHub. The new file and the commit are now visible there too.

git pull: bring changes from GitHub

On GitHub, edit the README.md file in the browser (pencil icon → Commit changes). This simulates a change made by someone else, or by you on another computer. Then, on your computer:

git pull
Updating 0c879b4..5e1a2f3
Fast-forward
 README.md | 2 ++
 1 file changed, 2 insertions(+)

If there is nothing new on GitHub, Git prints Already up to date.

OpozoriloGood habit

At the start of every work session, run git pull first and only then start editing files. This way you avoid conflicts.

git log and git diff: history and differences

git log --oneline     # short list of all commits
git diff              # what you changed but have not added with git add yet
git diff --staged     # what is staged for the next commit
5e1a2f3 (HEAD -> main, origin/main) Update README.md
0c879b4 Add test script
c82b3ae Initial commit

git init: a new repository from an existing folder

If the project already exists on your computer and you want to put it under version control now:

cd path/to/project
git init
Initialized empty Git repository in .../project/.git/

Git creates a hidden .git folder where it keeps the entire history (HEAD, objects, refs …). Do not edit or delete this folder, as that deletes the whole history.

To connect the local repository to GitHub, create an empty repository on GitHub (without a README) and then:

git remote add origin https://github.com/USERNAME/project.git
git push -u origin main
Opombaclone or init?
  • git clone: a copy of an existing repository from GitHub. This is the most common way and the one we use in the practicals.
  • git init: a new local repository that you connect to GitHub later.

Git in RStudio

In the practicals we work in RStudio, which has a built-in Git tab. The commands are the same as in Git Bash, you just run them with a click.

Connect RStudio to Git

  1. Tools → Global Options → Git/SVN.
  2. Tick Enable version control interface for RStudio projects.
  3. The Git executable field must contain the path to Git, on Windows usually C:/Program Files/Git/bin/git.exe. If the field is empty, find the file with Browse.
  4. Restart RStudio.

A new RStudio project from a GitHub repository

  1. File → New Project → Version Control → Git.
  2. Paste the HTTPS address of the GitHub repository into Repository URL.
  3. Choose a folder (Create project as subdirectory of), e.g. C:/Users/name/GitHub (not in OneDrive).
  4. Click Create Project.

In one step RStudio clones the repository (the same as git clone), turns it into an RStudio project and opens it. A Git tab appears in the top right, showing the current branch (main) in its top-right corner.

This is how you will open your repository EPG-2026-surname (Your EPG repository). Once the project exists, you open it next time by double-clicking the .Rproj file or via File → Open Project in RStudio.

OpombaAlready cloned the repository in the terminal?

Then do not clone it again. In RStudio choose File → New Project → Existing Directory and select the repository folder. RStudio recognises the Git repository by itself and shows the Git tab.

What is in the repository folder

After cloning in RStudio, the repository folder contains the following (hidden files and folders start with a dot):

EPG-2026-surname/
├── .git/                    # hidden folder: the entire history (this IS the repository)
├── .gitignore               # a FILE: what Git does not track
├── .Rproj.user/             # hidden folder with RStudio settings
├── EPG-2026-surname.Rproj   # RStudio project file
└── README.md                # description of the repository
What Created by Goes to GitHub?
.git/ Git when cloning no, it is the repository itself
README.md GitHub, when you create the repository yes
.gitignore GitHub (R template); RStudio adds a few lines yes
.Rproj RStudio yes
.Rproj.user/ RStudio no, it is in .gitignore

That is why right after opening the project the Git tab shows two changes: .gitignore (modified) and .Rproj (new, ?). This is expected; they go into your first commit.

The Git tab

Button / column Git command What it does
Staged checkbox git add stages the file for the commit
Diff git diff shows the changes line by line (green added, red deleted)
Commit git commit opens a window where you write a message and save the snapshot

.gitignore: what we do not upload to GitHub

The .gitignore file tells Git which files not to track. This is very important in population genomics:

  • GitHub rejects files larger than 100 MB. The eagle VCF file we will work with is almost 600 MB.
  • The data do not change during the analysis and are already stored elsewhere (e.g. in the Dryad repository that accompanies the paper). GitHub is for the code that turns data into results.
  • Intermediate files (PLINK .bed, .bim, .fam, .log …) can be recomputed at any time with your script.

Add the following to the end of .gitignore (the R template already contains .Rhistory, .RData and .Rproj.user/):

# --- data and intermediate files (EPG) ---
data/
*.vcf
*.vcf.gz
*.bed
*.bim
*.fam
*.ped
*.map
*.raw
*.log
*.nosex
*.exe

# --- rendered Quarto/Rmarkdown output ---
*_files/
*.html
OpombaWhat if I want to submit an HTML report?

If you want to upload a report to GitHub, delete the *.html line. For Quarto documents it is then recommended to add embed-resources: true to the header, so that everything (including figures) is in a single HTML file and you do not need the *_files/ folder.

NasvetFor the curious: publishing a report online (GitHub Pages, optional)

These instructions are made the same way: Quarto turns .qmd files into HTML, and GitHub Pages publishes it as a website.

  • .qmd is the source file (text and code) that you edit and keep in Git.
  • .html is the output that Quarto produces from .qmd. If you change the .qmd, you have to render the HTML again (Render).

Steps:

  1. Render the report with embed-resources: true in the header (all figures in one file) and name it index.html.
  2. Add the file to the repository (the *.html rule in .gitignore does not apply to this one file), then commit and push.
  3. On GitHub: Settings → Pages → Build and deployment → Deploy from a branch → main, folder / (root) → Save.
  4. After a minute or two the site is at https://username.github.io/repository-name/.

GitHub Pages for private repositories requires GitHub Pro (students get it free through GitHub Education). Otherwise use a separate public repository that contains only reports, no data.

OpozoriloIf a large file is already in a commit

If you accidentally added a large file to a commit, push will fail even if you later add the file to .gitignore. In that case, ask for help. The solution is to undo the last commit (git reset --soft HEAD~1), remove the file from the staging area (git rm --cached file) and commit again.

When something goes wrong: undoing changes

Situation Command
I changed a file and want the last saved version back git restore file.R
I added a file with git add but do not want it in the commit git restore --staged file.R
The last commit has a wrong message (not pushed yet) git commit --amend -m "New message"

Opozorilo

git restore file.R permanently discards unsaved changes in the file. Check with git diff before using it.

When two people work at the same time

What happens when two people (Ana and Bor) work on the same repository and both send their changes to GitHub?

Why this is good:

  • nobody can accidentally overwrite someone else’s work: Git rejects the push until you have all changes from GitHub,
  • both people’s work is kept: after git pull the history contains both commits, C and D,
  • Git does most of the merging itself; it only needs your help with a conflict.

The same happens when you work alone on two computers (e.g. at home and at the faculty). Hence the rule: always git pull before you start working.

Conflicts

A conflict happens when the same line of the same file was changed in two places (e.g. on GitHub and on your computer). On pull, Git writes markers into the file:

<<<<<<< HEAD
plot(pca$x[, 1], pca$x[, 2], col = "blue")
=======
plot(pca$x[, 1], pca$x[, 2], col = "red")
>>>>>>> origin/main

The upper part is your version, the lower part is the version from GitHub. Manually keep the correct line, delete the <<<<<<<, ======= and >>>>>>> markers, and then git add, git commit and git push.

When working in your own repository from one computer, you avoid conflicts by consistently following the pull → work → commit → push loop.

Branches

Branches, merging and conflicts are not required for submitting the practicals. For the practicals, clone, status, add, commit, push and pull are enough. This part is for self-study and for team projects.

Branches let you develop new things or try out ideas without breaking the working main version (main). In the practicals you will mostly work on main, but branches are the basis of every team project.

  • main should stay as stable as possible,
  • each person or each new feature gets its own branch,
  • when the work is finished and tested, the branch is merged back into main.

Creating and switching branches

git branch                 # list local branches (* = current)
git switch -c new-plot     # create a new branch and switch to it
git switch main            # go back to main
git branch -d new-plot     # delete the branch (once it is merged)
Opombagit switch or git checkout?

In older tutorials and figures you will often see git checkout (git checkout -b new-branch). The command works, but it does two different jobs: switching branches and restoring files, which confuses beginners. Newer Git commands split them: git switch for branches, git restore for files. In the practicals we use switch.

Example of working on a branch

git switch -c new-plot
# ... edit files ...
git add .
git commit -m "Add PCA plot coloured by country"
git push -u origin new-plot

On the first push of a new branch, GitHub prints a link to open a Pull Request. This is a proposal to merge the branch into main, which collaborators can review.

Merging: git merge

Switch to the branch you want to update (usually main) and merge the other branch into it:

git switch main
git merge new-plot
git push
Updating 0c879b4..a09a19b
Fast-forward

Git Bash teaches you how Git really works. Once you understand the commands, graphical tools are convenient:

  • RStudio (Git tab): for the practicals,

You can also edit files in the browser on GitHub. This is fine for small README changes, but not for code, because you cannot run and check it before the commit.

Command summary

git config --global user.name "Name Surname"   # one-time setup
git config --global user.email "address"

git clone <url>              # copy a repository from GitHub
git init                     # new local repository
git status                   # what has changed
git add <file>               # stage a file for the commit
git add .                    # stage all changes in the folder
git commit -m "message"      # save a snapshot
git push                     # send commits to GitHub
git pull                     # bring and merge changes from GitHub
git log --oneline            # commit history
git diff                     # unstaged changes

git restore <file>           # discard changes in a file
git restore --staged <file>  # remove a file from the staging area

git branch                   # list branches
git switch -c <name>         # create a branch and switch to it
git switch <name>            # switch to an existing branch
git merge <name>             # merge a branch into the current branch
git branch -d <name>         # delete a branch

Homework: preparation for practical 2

In all following practicals we will analyse genomic data of the white-tailed eagle (Haliaeetus albicilla) from the paper:

Hansen, C. C. R., Láruson, Á. J., Rasmussen, J. A., et al. (2023). Genomic diversity and differentiation between island and mainland populations of white-tailed eagles (Haliaeetus albicilla). Molecular Ecology, 32, 1925–1942. https://doi.org/10.1111/mec.16858

The paper is open access: PDF of the paper. Read it and create a file E1_git/eagle_paper.md in your repository, in which you briefly answer (in a few sentences) the following questions:

  1. What is the main research question of the paper? Why is it interesting that a species with a high dispersal capacity is genetically structured?
  2. Which countries are the samples from? Which populations are island and which are mainland populations?
  3. What are the historical samples and why did the authors include them in addition to the contemporary ones?
  4. What type of data did they use (sequencing, number of SNPs) and how did they filter the data?
  5. List the analyses they performed (e.g. genetic diversity, FST, PCA, ADMIXTURE, inbreeding, effective population size). Which figure or table shows the result of each analysis?
  6. What are the main findings on the diversity and inbreeding of island populations compared to mainland populations?
  7. Which four historical events are thought to have shaped the decline in effective population size?
  8. Explain in your own words: founder effect, genetic drift, inbreeding, philopatry, effective population size (Ne).

Submit the file with commit and push before practical 2. In practicals 2–6 we will repeat some of these analyses ourselves and at the end check whether we reach the same conclusions as the authors.

For the curious: working in a team

In larger projects with several collaborators, the team agrees on rules for branches. Simple rules that prevent a lot of trouble:

  1. do not experiment directly on main,
  2. always pull before you start working,
  3. create a branch with a descriptive name for every new thing (new-plot, fix-readme),
  4. merge the branch only when the code works,
  5. write meaningful commit messages.

One of the best-known conventions is Git flow:

Branch Role
main stable, released code
develop ongoing development, integration of new features
feature/* new features (from develop)
release/* preparing a new version (from develop)
hotfix/* urgent fixes (from main)

Merge or rebase?

Both commands bring work from one branch into another, but they treat history differently.

Merge keeps the actual history and creates an additional commit that joins the two branches:

A---B---C---F    (main, F = merge commit)
         \ /
          D---E  (branch)

Rebase “replants” your commits on top of the other branch, so the history is linear. The commit identifiers (hashes) change in the process:

A---B---C---D'---E'
Merge Rebase
History keeps branches linear, cleaner
Safety on shared branches safer can confuse collaborators
Conflicts resolved once may appear for each commit

In the practicals we use merge. Rebase is useful once you are comfortable with the basics of collaboration.
